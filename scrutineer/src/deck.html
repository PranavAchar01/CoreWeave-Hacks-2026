Scrutineer is an agent that rebuilds its own harness, and we draw that harness as a race car so you can watch it change. We built it at CoreWeave Hacks: Agent Loops. It starts from the same idea as Andrej Karpathy's autoresearch: there, an agent edits one training file, trains for a fixed five minutes, checks a single metric and keeps or discards the change, about a hundred experiments a night. Every tool in our loop sits behind an adapter that reports which backend actually served it, and scrutineer doctor prints that table.

Each page is audited for accessibility with axe-core and timed twice: once on a practice split the agent can see, and once on a sealed held-out split it never sees. The evaluator logs every race to the Weave Evals tab, one row per task, with the same scores the gates read. That seal matters because an agent that keeps checking against the same test starts to learn the test. That is exactly the problem Blum and Hardt's Ladder and Dwork and colleagues' reusable holdout were built to solve, and one of our gates is a Ladder. Code the agent writes is tested in the first isolated backend that answers: CoreWeave and W&B Sandboxes first, then Docker with no network. Managed sandboxes aren't enabled for our account, so ours ran in Docker.

Autoresearch judges a whole run by one number. Scrutineer instead traces every failing page back to the one component that caused it, much as TextGrad sends feedback back to individual parts of a compound AI system. Every model call and feedback row goes to a local append-only store and is mirrored to W&B Weave, so the build, audit, replay and blame steps can be inspected there. There are ten components: retrieval, the model, sampling, verification, curriculum, the proposer, budget, audit, memory and deploy. After a season, scrutineer runs writes one W&B run per component per round, with its blame and whether its change moved the held-out score. Curriculum picks practice tasks, like Voyager's automatic curriculum, and memory records findings for next time, the way Reflexion keeps its reflections. Each generation, memory also writes its debrief as a marimo notebook.

The loop picks the component with the best expected gain per dollar, and that component writes a change to itself. The loop's typed decisions go through one endpoint whose first backend is TypeSafe System1; the recorded season had no TypeSafe key, so a local policy answered. Our version of its archive is W&B Registry, where every component version is linked to the version it came from.

Each row carries the hash of the row before it and an Ed25519 signature. Nothing else in the loop can append.

    

  

  
The change then has to clear a set of gates, including size, novelty, evidence, regression, a check that both splits agree, and cost. It also has to pass its marimo debrief: the notebook must pass marimo check, run as a script and reproduce the promotion decision. It is kept only if every gate passes, and every kept change is written to a signed ledger, our version of autoresearch's experiment log and the Darwin Gödel Machine's archive of agents. After each attended generation, the loop asks ARIA which component's changes moved the held-out score, writes the answer into the next round's hypothesis, and records whether ARIA agrees with the ledger.

On the car, wings are retrieval, the floor is verification and tyre compound is sampling, so a kept change visibly rebuilds the car. When a change is kept, the champion alias in W&B Registry moves to the new version, and only the auditor is allowed to move it, so the next race always uses the promoted version. Where the car sits on the lap shows how far the current run has got.
